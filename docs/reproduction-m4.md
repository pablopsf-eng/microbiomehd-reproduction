Committed summary of M4's result, mirroring `docs/reproduction-m2.md`/

## Part A: does CLR change the shared-response conclusion?

**Generated by:** `uv run scripts/clr_shared_response.py`, run 2026-09-23
(re-run after the `CONDITION_FILTER` fix — prior run
was 2026-09-21 after the `SAMPLE_TYPE_FILTER` fix, original run was
2026-09-18; numbers below are the fresh, post-`CONDITION_FILTER` ones).
**Environment:** Python 3.12.3, pandas 3.0.5, numpy 2.5.3, scikit-learn
1.9.1, scipy 1.18.1, statsmodels 0.15.0, pyyaml 6.0.3
(`results/clr_shared_response/provenance.json`).

Method, in one paragraph: run `mbhd.shared_response.build_qvalue_matrix`
twice over the same 29 successfully-reproduced datasets (`ob_zupancic`
excluded — see below) — once with the default Euclidean
`differential_abundance`, once with `abundance_transform=functools.
partial(mbhd.compositional.clr, pseudocount_fn=mbhd.compositional.
multiplicative_replacement)` — then apply the identical, already-verified
labelling rule to each, restricted to `mbhd.
shared_response.PUBLISHED_EXCLUSIONS` (the primary-target exclusion set M3
already uses), and diff the two label sets lineage by lineage.

`ob_zupancic` fails identically under both paths (`ZeroReadSampleError`,
before `abundance_transform` is ever applied — the zero-total-reads check in
`mbhd.abundance.to_genus_abundance` runs first) — 29 of 30 datasets produce
a comparison either way, matching M3's own D0 result exactly.

| comparison | Euclidean pool | CLR pool | common lineages | flipped label | only Euclidean | only CLR |
| --- | --- | --- | --- | --- | --- | --- |
| full-29 | 152 | 247 | 145 | 51 (35%) | 7 | 102 |
| clean-27 | 133 | 223 | 127 | 30 (24%) | 6 | 96 |

`clean-27` is `CLEAN_27` in both scripts — 27 datasets whose genus set
reproduces exactly, up from `CLEAN_23` before
the `CONDITION_FILTER` fix added `edd_singh`/`hiv_lozupone`/`nash_wong`/
`ob_goodrich` to that set.

**Read plainly, not softened:** CLR changes the conclusion substantially,
not marginally. The CLR-transformed pool is 1.6–1.7x larger than the
Euclidean one on both tiers, and among lineages both approaches have an
opinion on, 24–35% get a different label (health/disease/mixed/not-in-pool).
This is a real, quantified disagreement between two statistically valid
ways of running the same Kruskal-Wallis + Benjamini-Hochberg pipeline over
the same underlying counts — not a bug in either path (Kruskal-Wallis makes
no Euclidean-geometry assumption and is exactly as valid on CLR values as on
raw relative abundances -- it is rank-based), and not resolved here. Every flipped lineage is individually listed with
both labels in `results/clr_shared_response/{full29,clean27}.csv`.

### Mechanism, tested (2026-09-21): CLR eliminates ties, but not via the pathway first guessed

An earlier version of this section offered an unconfirmed guess: CLR's
zero-replacement turns tied-at-zero cells into distinct values, and
`mbhd.stats.kruskal_wallis`'s tie correction is most conservative when
ties are heaviest, so "fewer ties would mechanically tend to produce
smaller p-values." Re-deriving the formula while planning how to test
this surfaced a real problem with it: `kruskal_wallis` computes `H =
H_uncorrected / C`, and `C` (the tie-correction factor) is *smaller* when
ties are heavier — dividing by a smaller `C` makes `H` *larger*, the
opposite of "fewer ties → smaller p" for the tie-correction step in
isolation. The guessed mechanism, as literally stated, pointed the wrong
way; it needed testing, not trusting.

**Generated by:** `uv run scripts/clr_tie_investigation.py`, run
2026-09-23 (re-run after the `CONDITION_FILTER` fix — prior run was
2026-09-21 after the `SAMPLE_TYPE_FILTER` fix, ~24s; numbers below are the
fresh, post-`CONDITION_FILTER` ones, materially unchanged). A one-off
diagnostic (not a pipeline component): recomputes `mbhd.stats.
kruskal_wallis`'s own tie-correction factor `C` and uncorrected statistic
`H_uncorrected` outside the (unmodified, still heavily-verified) function,
for both representations, across every one of 2,736 genus/dataset
comparisons in the full-29 run — and self-checks every single one against
`kruskal_wallis`'s own real `(H, p)` output on the identical arrays (all
2,736 passed; a mismatch would have aborted the script, not produced a
"finding").

| | Euclidean | CLR |
| --- | --- | --- |
| mean tie-correction factor `C` | 0.549 | **1.000 (exactly, zero variance, all 2,736 comparisons)** |
| mean `H_uncorrected` | 3.38 | 9.57 |
| median `H_uncorrected` | 0.47 | 2.57 |

| correlation with `Δ(-log10 p)` (CLR more significant when positive) | r |
| --- | --- |
| `ΔC` (the originally-named tie-correction-factor pathway) | 0.42 |
| `ΔH_uncorrected` (the competing, un-named raw rank-separation pathway) | **0.98** |

**Read plainly: the hypothesis's premise is confirmed outright, but the
named mechanism is not what drives the result.** CLR does eliminate ties
completely — `C_clr` is exactly `1.0` for all 2,736 comparisons, zero
exceptions, because each sample's own distinct geometric-mean centering
constant (subtracted in the CLR transform) almost certainly breaks any
exact tie that survives the zero-replacement step, even between samples
replaced with the identical pre-centering value. But the tie-*correction*
formula step itself only modestly correlates with which genera end up
more significant under CLR (`r=0.42`). What actually drives it, almost
one-to-one (`r=0.98`), is that heavy ties directly suppress the
**uncorrected** rank-sum statistic before any correction is even applied:
averaging many tied observations (mostly exact zeros) into one shared rank
collapses real between-group rank differences into a shared, non-
discriminating value, diluting `H_uncorrected` itself — CLR's median
`H_uncorrected` is over 5x the Euclidean median. `ΔC` and
`ΔH_uncorrected` are themselves correlated (`r=0.43`, `results/
clr_tie_investigation/comparisons.csv`), consistent with both being
downstream symptoms of the same root cause (tie-heavy raw ranks), not two
independent mechanisms — the correction-factor pathway is the smaller,
secondary one. 58.2% of all 2,736 comparisons are more significant under
CLR (`Δ(-log10 p) > 0`), consistent with, though smaller in magnitude
than, the ~1.6x larger reported pool size (which is further filtered by
the ≥2-diseases labelling rule, not a direct count of "more significant
comparisons"). Per-comparison numbers: `results/clr_tie_investigation/
comparisons.csv`.

## Part B: does the shared-response signature generalize to an unseen study?

**Headline result, stated up front:** the reported classifier result is the
**CLR-featured** shared-response arm, mean AUC-ROC **0.635** / AUC-PR **0.720**
("Headline result: CLR-featured classifier" below). The Euclidean
(relative-abundance) run (0.603) is the methodological baseline this was
compared against and is described first, since the leak-free design and
the leakage-quantification work were done on it first, chronologically.
Model tuning (`class_weight="balanced"` + nested-CV-tuned regularization)
was also tried on top of CLR and reached 0.646 (refreshed 2026-09-24 after
both the `SAMPLE_TYPE_FILTER` and `CONDITION_FILTER` fixes — see "Appendix:
model tuning" for the full, current numbers) — a real, further gain, but
one judged not to justify its added runtime (55 minutes vs. 8.5) and
complexity, and kept as a secondary appendix rather than the reported
number ("Appendix: model tuning" at the end of this Part, with the
reasoning behind that call).

**Generated by:** `uv run scripts/classifier.py`, run 2026-09-23 (re-run
after the `CONDITION_FILTER` fix — prior run
was 2026-09-21 after the `SAMPLE_TYPE_FILTER` fix, original run was
2026-09-18; numbers below are the fresh, post-`CONDITION_FILTER` ones), 200
permutation-null repeats (the pre-set default — not reduced).
**Environment:** same as above, plus scikit-learn 1.9.1 as a new runtime
dependency (`results/classifier/provenance.json`).

Method, in one paragraph: pool per-study genus relative abundance
(`mbhd.classifier.pooled_feature_matrix`, reusing `mbhd.abundance`'s and
`mbhd.labels`'s already-verified building blocks unchanged) across the same
29 datasets as Part A, grouped by `DatasetInfo.folder` — **27 folders** (29
datasets, two pairs of which share a folder; an earlier draft design
stated 28, an arithmetic slip, corrected -- the design itself, grouping
by folder rather than dataset ID, is unaffected). Fit `StandardScaler` + `LogisticRegression`
inside each of scikit-learn's `LeaveOneGroupOut` folds
(`mbhd.classifier.leave_one_group_out_auc`) — the scaler and classifier
never see the held-out folder's own data, by construction of `sklearn.
pipeline.Pipeline`.

### Feature-selection leakage: found, fixed, and quantified

The first version of this script chose its primary (then-59-genus, now
55-genus after the `SAMPLE_TYPE_FILTER` fix) shared-response feature list
once, globally, from all 29 datasets' own significance calls,
*before* the LOFO loop began — matching the original design wording
literally ("the M3 full-29-vs-GitHub shared-response genus pool" as
one fixed, already-committed list). Both the `verifier` and `code-reviewer`
review passes independently flagged this as a feature-selection leakage
path: a held-out fold's own case/control labels could have helped decide
whether a borderline genus crossed the "significant in ≥2 distinct
diseases" threshold and made it into the feature list that same fold is
later scored on — this project's rule that "cross-validation must wrap the entire
pipeline, not just the model" was satisfied for the
`StandardScaler`/`LogisticRegression` fit boundary but not for this
upstream step. Pablo asked for this fixed rather than only documented.

**Fix:** `mbhd.classifier.leave_one_group_out_auc_dynamic_features` (new)
recomputes each fold's feature list from *only that fold's training
datasets*' own significance calls — the held-out folder never contributes
to its own feature selection. `scripts/classifier.py` now runs both the
original fixed **global-pool** version (kept, for comparison) and the new
per-fold **leak-free** version side by side for both label-derived arms
(`shared_response`, `disease_specific`); the `full` arm is unaffected by
this fix since it is not label-selected at all (every genus ever
reproduced, regardless of significance).

| arm | global-pool (leaky) mean AUC-ROC | per-fold (leak-free) mean AUC-ROC | leakage effect |
| --- | --- | --- | --- |
| **shared-response (Euclidean baseline)** | 0.607 (55 features, fixed) | **0.603** (39–55 features, varies per fold) | **−0.004 — negligible** |
| disease-specific (reported) | 0.549 (99 features, fixed) | 0.555 (82–108 features, varies per fold) | +0.006 |
| full genus set (reported, unaffected by the leak fix) | 0.546 | 0.546 (same number, arm not re-run) | n/a |

**Read plainly: the leakage was real in principle but turned out to be
negligible in practice for the Euclidean-baseline result** — 0.607 vs. 0.603 is well
within noise, not a meaningful inflation. This applies to the Euclidean
baseline specifically; the CLR headline result below uses this same
leak-free design and inherits the same conclusion. This is itself a
useful, honestly-obtained finding: it says the shared-response signal is
not an
artifact of the feature list quietly peeking at test-fold labels. The
disease-specific arm moved slightly the other way (leak-free is *higher*,
+0.006) — small enough not to change any qualitative conclusion, but a
reminder that "leakage inflates the number" is not automatic in every
direction; it depends on the specific fold/label structure. Per-fold
feature counts for the leak-free arms (`n_features_min`/`n_features_max`
in `results/classifier/summary.json`) show real fold-to-fold variation (39
to 55 genera for shared-response) — expected, since removing one fold's
worth of studies can drop a borderline genus below the "≥2 distinct
diseases" threshold.

Per-fold numbers: `results/classifier/lofo_{shared_response,
shared_response_global_pool,disease_specific,disease_specific_global_pool,
full}.csv`.

### Permutation null, baseline (200 within-folder label-shuffle repeats, seed 42, leak-free)

`mbhd.classifier.permutation_null_auc_dynamic` (new) — the null is judged
under the same leak-free, per-fold feature-selection design as the real
result it is compared against, not the original fixed-pool one. This is
the Euclidean baseline's own null; the CLR headline result has its own
null table below, in its own section.

| | value |
| --- | --- |
| null mean AUC-ROC | 0.501 |
| null std AUC-ROC | 0.0146 |
| real (baseline arm, leak-free) mean AUC-ROC | 0.603 |
| empirical p-value: `(b+1)/(m+1)`, `b`=repeats >= real mean, `m`=200 | 0.005 (0/200 at or above; North, Curtis & Sham 2002's standard unbiased Monte Carlo estimator — never the raw `b/m`, which reported an impossible exact `0.0` in an earlier, incorrect version of this script caught by `code-reviewer`) |

The null's own mean lands almost exactly at 0.5 (0.5006) — the self-check
named in advance ("the null distribution's own mean
AUC is ~0.5 by construction") holds on the real data, not only in the
synthetic unit test. The real baseline-arm mean sits roughly 7.0 null
standard deviations above the null's own mean; none of the 200 shuffled
repeats reached it. This is evidence *against* the null hypothesis that the
shared-response signature carries no folder-transferable signal — not proof
of a specific biological mechanism, and not comparable to a textbook
parametric p-value (there is no closed-form null distribution assumed here,
only the empirical one actually run).

### Headline result: CLR-featured classifier

The classifier could plausibly be improved, given the modest 0.603
Euclidean-baseline number above. Batch/study-effect correction (this design's
own biggest named weakness — no correction is applied when pooling 27
independently-sequenced studies) was the best-motivated lever available;
the concrete step taken was feeding the classifier CLR-transformed values
instead of raw relative abundances for the *same* leak-free,
per-fold-selected shared-response gene set — isolating the value
representation as the only changed variable, not the genes themselves
(`mbhd.classifier.pooled_feature_matrix` gained an optional
`abundance_transform` parameter, the same insertion point and name
`differential_abundance` already uses; default `None` regression-tested
byte-identical). **Decided (2026-09-18, Pablo): absent-genus fill stays
`0.0`** even under CLR, where `0.0` means "average" rather than "low" — the
mismatch is real and documented in `mbhd.classifier.pooled_feature_matrix`'s
own docstring, kept anyway as the least assumption-laden choice rather than
inventing a second, unverified fill convention on top of the already-decided
CLR zero-replacement one.

~8m31s; numbers below are the fresh, post-`CONDITION_FILTER` ones), 200

| --- | --- | --- | --- | --- | --- | --- |
| relative abundance (baseline) | 0.603 | 0.689 | 0.5006 | 0.0146 | ~7.0 | 0.005 |
| **CLR (headline)** | **0.635** | **0.720** | 0.4995 | 0.0148 | ~9.1 | 0.005 |

**This is the project's reported Part B result.** CLR features helped, by
a real, moderate amount — AUC-ROC +0.032, AUC-PR +0.031 over the baseline,
both null-relative distances larger, not just the raw number. This is not
dramatic (0.635 is still well short of a strong discriminator) but is a
genuine, checkable improvement consistent with the compositional-data
reasoning that motivated trying it: relative abundances are constrained to
sum to (roughly) a constant per sample, which a linear classifier's own
coefficients do not account for, while CLR's log-ratio representation
removes that constraint. Both null distributions land close to 0.5 as
expected (0.5006 / 0.4995), so the comparison is apples-to-apples — the
improvement is not an artifact of a shifted null. Per-fold numbers:
`results/classifier/lofo_shared_response_clr.csv`,
`permutation_null_clr.csv`.

A more flexible (non-linear) model was explicitly not tried, given the
small per-fold sample sizes relative to feature count. A further lever
(class-weight + nested-CV regularization tuning) was tried on top of this
CLR result and reached a real additional gain (0.646, refreshed 2026-09-24
after both the `SAMPLE_TYPE_FILTER` and `CONDITION_FILTER` fixes) — kept as
a secondary appendix, not adopted as this section's reported number; see
"Appendix: model tuning" below for the reasoning.

### Secondary: within-study stratified k-fold (reported, not required)

The global-pool (fixed 55-genus) shared-response feature set, but each of
the 29 datasets' own samples split and evaluated entirely within that one
study (`mbhd.classifier.within_study_cv_auc`, `n_splits` capped at the
minority class's own count when smaller than 5 — every one of the 29
datasets used the full 5 splits; `results/classifier/within_study.csv`).
The global (not leak-free) pool is used here deliberately: this analysis
never claims cross-study generalization in the first place, so the
feature-selection leakage path this Part's headline result had to close
does not apply to it.

Mean AUC-ROC across all 29 datasets: **0.675** — higher than the LOFO
result (0.603 baseline / 0.635 headline), consistent with the framing
set out beforehand: a within-study score cannot distinguish a real, transferable
biological signal from that one study's own technical/batch artifact, so a
higher within-study number is expected regardless of which explanation is
true, and is reported as context, not evidence either way.

## Appendix: model tuning (tried, not adopted as the headline result)

**Refreshed 2026-09-24** (M5's own `--tune`+`--batch-correct` follow-up
happened to require the first real `--tune`-only run since the
`SAMPLE_TYPE_FILTER`/`CONDITION_FILTER` fixes — the numbers below are now
current, not stale). Prior state, kept visible rather than silently
erased: this appendix was **not re-run after `SAMPLE_TYPE_FILTER`**
(decided 2026-09-21) or **after
`CONDITION_FILTER`** (2026-09-23) — both times because the
~55-minute cost wasn't justified for a number that isn't the reported
result. Both staleness windows are now closed.

**This is still a secondary experiment, not this project's reported Part B
number** — the headline result stays the CLR run above (0.635). Kept here
because the code is correct, tested, and reviewed, and because the
negative-on-the-baseline finding (tuning alone made things worse) is
itself informative — not because the tuned CLR number was adopted as the
answer.

**Why it was demoted rather than adopted, decided explicitly (2026-09-18,
Pablo, reaffirmed 2026-09-24 for the fresh numbers), not left implicit:**
the additional gain over CLR alone is small (+0.011 AUC-ROC, 0.635 →
0.646) relative to its cost — a real runtime cost (see the timing note
below) and materially more code (a second model variant, a CLI flag, a
helper function, four more tests, more documentation surface to
maintain). There is also a subtler reason: reporting "the best of four
{representation} x {model} combinations tried" invites more scrutiny of
researcher-degrees-of-freedom than reporting one well-motivated change
(CLR) that worked — CLR has a clean, single-variable story (compositional
data isn't Euclidean); "CLR plus the right amount of regularization for
it" is a smaller, harder-to-defend effect on top of that story. The code
and results are kept, both directions honestly reported, but 0.635 (the
current CLR headline above, not this appendix's own 0.646) is what this
project claims.

Pablo asked to also try the second lever (`class_weight="balanced"` +
regularization-strength `C` tuned by nested CV), **on top of, not instead
of**, the CLR features above — i.e. all four combinations
{relative_abundance, CLR} x {plain, tuned} were run so the two changes
could be judged both separately and together. Planned first
(`EnterPlanMode`) since this was a real design decision with a genuine,
empirically-grounded runtime tradeoff, not a small edit: a timing probe
(one fit, real-shaped data) found `sklearn.linear_model.LogisticRegressionCV`
(class-weighted, 5 inner folds, sklearn's own default 10-value `C` grid) is
~5x slower per fit than plain `LogisticRegression` — Pablo chose to keep
the full 200 permutation-null repeats anyway (`mbhd.classifier.
_tuned_pipeline`, `scripts/classifier.py --tune`). The inner 5-fold CV that
picks `C` sees only whatever data `.fit()` receives -- for a LOFO fold
that's the outer training fold alone, so the nested-CV train/test boundary
follows from the same train-fold-only `fit` call `StandardScaler` already
relies on. `scoring="roc_auc"` was set explicitly (sklearn's own scoring
default is mid-transition to `neg_log_loss` in a future version, confirmed
by a live `FutureWarning`) — matches this project's own chosen metric,
not sklearn's changing default.

apples-to-apples, not an artifact of a shifted null.

  the "too many zeros" degenerate case does not arise in practice.
- The classifier's original fixed-global-pool feature selection (a real
  leakage path, not an edge case anticipated in advance) was found by
  review and fixed by request, not left as a documented-only caveat — see
  "Feature-selection leakage: found, fixed, and quantified" above. The
  0.603 baseline number is the leak-free one; 0.607 (the original,
  slightly-leaky number) is kept and reported alongside it so the size of
  the effect (negligible, here) is a real, checked number rather than an
  assumption.
- The reported Part B result is the CLR-featured classifier (0.635), not
  the Euclidean baseline (0.603) — stated at the top of Part B and again in
  "Headline result: CLR-featured classifier". Model tuning reached a
  higher number still (0.646, refreshed 2026-09-24 after both the
  `SAMPLE_TYPE_FILTER` and `CONDITION_FILTER` fixes) but was deliberately
  not adopted as the reported result (`## Appendix: model tuning`) — a
  scope decision, not an oversight.
