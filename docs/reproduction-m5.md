# M5: batch/study-effect correction for the LOFO shared-response classifier

Committed summary of M5's result, mirroring `docs/reproduction-m2/m3/m4.md`'s
structure. Regenerable: `uv run scripts/classifier.py --features clr
--batch-correct` writes its full outputs to `results/classifier/`
(gitignored); this file is the durable, human-readable record of what that
run found.

**Read this before the numbers below**: like M4's own two sub-questions,
there is no published ground truth for "does batch correction change the
LOFO result" -- "verified" means the mechanics (the from-scratch ComBat
implementation's math, its leak-free wiring into the LOFO loop) are proven
correct (`tests/test_batch.py`, `tests/test_classifier_verification.py`),
and the *real* result is then reported plainly against the already-adopted
M4 headline, not checked against ground truth, because none exists.

## Method, in one paragraph

M4's own biggest acknowledged weakness -- no correction for study-to-study
technical batch effects when pooling 27 independently-sequenced folders --
is addressed directly: `mbhd.batch` (new module) implements parametric
ComBat (Johnson, Li & Rankin 2007) from scratch, verified against
`pycombat` (dev-only dependency, never imported at runtime). A new
`fold_transform` hook on `mbhd.classifier.leave_one_group_out_auc_dynamic_
features`/`permutation_null_auc_dynamic` applies it (or the simpler
per-batch mean-centring lever) to each LOFO fold's already-column-selected
feature matrix, immediately before the classifier is fit -- leak-free by
construction: the hook never receives the held-out fold's own labels or
identity, only its feature rows. Six comparison rows, all on the CLR
shared-response feature set (M4's own adopted representation, not
re-litigated here):

| # | row | mean AUC-ROC | mean AUC-PR | null mean / std | null std devs above | n_folds improved / worse / same (vs. row 1) |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | no correction (M4 headline) | 0.635 | 0.720 | 0.500 / 0.015 | ~9.1 | -- |
| 2 | per-batch mean-centring | 0.650 | 0.736 | 0.500 / 0.017 | ~8.9 | 17 / 9 / 1 |
| **3** | **ComBat, no covariate, leak-free (primary)** | **0.647** | **0.729** | 0.500 / 0.017 | ~8.5 | **19 / 7 / 1** |
| 4 | ComBat, covariate, training-side only, leak-free | 0.619 | 0.719 | 0.502 / 0.015 | ~7.6 | 13 / 14 / 0 |
| 5 | ComBat, no covariate, fit once globally (leaky, warning) | 0.651 | 0.733 | -- | -- | -- |
| 6 | ComBat with covariate, fit once globally *including held-out labels* (leaky + label leak, warning) | **0.769** | 0.816 | -- | -- | -- |

**Generated by:** `uv run scripts/classifier.py --features clr
--batch-correct`, run 2026-09-24, 200 permutation-null repeats per row
(rows 2-4; rows 5-6 have no null, by design -- see below), **~40 minutes**
end-to-end (process start 13:07, `provenance.json`'s own
`generated_at_utc` 13:47:03 local) -- matching the pre-implementation timing probe's
own extrapolated estimate (~40 minutes, from a 3-repeat/10-repeat
marginal-cost calculation) closely, unlike M4's own tuning run which ran
well over its pre-run estimate. **Environment:** Python 3.12.3, pandas
3.0.5, numpy 2.5.3, scikit-learn 1.9.1, scipy 1.18.1, statsmodels 0.15.0,
pyyaml 6.0.3, **pycombat 0.20** (`results/classifier/provenance.json`).

## Adoption rule (fixed before the run)

Row 3 becomes the new headline only if it beats row 1 *and* its
permutation null stays centered near 0.5. **Both hold:** 0.647 > 0.635, and
the null mean (0.5003) is indistinguishable from every other null in this
project's history. **Row 3 (ComBat, no covariate, leak-free) is therefore
this project's new Part B headline, replacing M4's uncorrected 0.635.**
A same-day follow-up asked whether tuning this adopted arm further is
worth it (matching M4's own tuning question, now asked of the ComBat
result) — real gain, not adopted, for the same reasons M4's own tuning
wasn't: see "Appendix: tuned ComBat" below.

## Read plainly, in the order the six rows raise questions

- **Batch correction genuinely helps, by a real, checkable, modest
  amount.** 0.635 -> 0.647 (+0.012 AUC-ROC, +0.009 AUC-PR) is not
  dramatic, but 19 of 27 folds individually improved, only 7 got worse,
  and 1 tied bit-for-bit (`t1d_mejialeon_results`) -- a real majority
  effect, not one or two folds driving the whole mean. The null
  distribution stays centered at 0.500, so this is not an artifact of a
  shifted null the way a naive covariate fit would be (see rows 5-6
  below).
- **The simplest lever (row 2, per-batch mean-centring) does *slightly*
  better on the mean (0.650 vs. 0.647) but improves fewer folds (17 vs.
  19).** Read plainly rather than picked around: ComBat's added machinery
  (scale correction, empirical-Bayes shrinkage) does not clearly beat the
  simplest possible correction on this data by its headline mean alone --
  but it is more consistent across folds (19/27 vs. 17/27 improved), and it
  is the row named as primary *before* the run per the adoption
  rule fixed in advance, not chosen after seeing which number was larger. Row 2 is reported
  honestly alongside row 3, not hidden because it happens to have a
  slightly higher mean.
- **The covariate arm (row 4) makes things *worse*, not better** (0.635 ->
  0.619). This is a real, reported negative result, not filtered out for
  not fitting the narrative -- consistent with the prediction
  made beforehand (batch and disease-comparison identity are almost perfectly
  confounded at the dataset level, and Nygaard, Rødland & Hovig 2016's
  documented exaggeration effect for covariate ComBat on unbalanced
  per-batch case fractions, which this dataset has in abundance -- folder
  case fractions here range from 8/29 to 292/349). Preserving the
  case/control contrast during training-side correction does not
  straightforwardly help when "batch" and "which disease" are nearly the
  same variable.
- **Row 5's own gap from row 3 (0.651 vs. 0.647, +0.004) does *not*
  cleanly isolate the cross-batch-fit ComBat leak, and an earlier
  version of this section wrongly claimed it did.** Row 5 differs from
  row 3 in two independent ways at once -- it reuses the fixed, globally-
  selected 55-genus feature set (the *same*, already-known feature-
  selection leak M4 quantified as 0.607-vs-0.603, unrelated to ComBat) as
  well as fitting `combat()` once globally instead of per-fold leak-free.
  A `verifier` review decomposed the two directly on the real data
  (`tests/test_batch_m5_row5_leak_decomposition_verification.py`, a
  durable regression check, not a one-off calculation): holding the
  feature set fixed either way and varying only whether ComBat is fit
  globally or per-fold leak-free changes the mean AUC-ROC by
  **-0.0000 in both directions** -- the ComBat cross-batch-fit
  leak is, on this data, indistinguishable from zero. The feature-set
  difference alone (0.6510 fixed-global vs. 0.6472 per-fold, ComBat kept
  leak-free both times) accounts for essentially the entire reported gap
  (+0.0037). Row 5 is kept in the table because it still correctly shows
  that fitting ComBat once globally does not, by itself, meaningfully
  change the number here -- but it is *not* evidence that the cross-batch-fit leak
  is real-but-small, since the experiment as run cannot distinguish "the
  leak is small" from "the leak doesn't exist here" -- this project's own
  standard for not overstating what a result actually shows.
- **Row 6 (naive global ComBat, with covariate, including held-out labels)
  quantifies the held-out label leak -- and it is not small.** 0.769 vs.
  0.619 (leak-free row 4): a **+0.15 AUC-ROC inflation**, by a wide margin
  the largest leakage effect measured anywhere in this project's history
  (M4's own feature-selection leak was 0.003-0.012). This is the exact,
  concrete failure mode (the held-out label leak) predicted in the abstract
  (`X_ij·β_g` entering a held-out sample's own corrected feature value) --
  seeing the real number confirms it was not a theoretical worry. Shown
  here explicitly as a warning, never offered as a candidate result; the
  leak-free hook design (the `fold_transform` signature never receives a
  held-out fold's own labels at all) makes this specific mistake
  structurally impossible to reproduce by accident in this project's own
  code, not merely discouraged by convention.
- **The batch≈disease confound is not resolved by anything
  here, and no row claims to.** Rows 3 and 4 differ only in whether the
  case/control contrast is preserved during training-side correction; the
  fact that preserving it makes things worse, not better, is consistent
  with the confound being real, not with the confound being solved.

## What was *not* run, and why (explicitly out of scope)

`--tune` (nested-CV model tuning) was not combined with `--batch-correct`
in this milestone -- two changed variables at once, against this project's
own single-variable-at-a-time discipline (the same reasoning M4 used to
keep tuning a secondary appendix rather than stacking it onto the CLR
headline). **Updated, same day:** a follow-up did run exactly this
combination at Pablo's request -- see "Appendix: tuned ComBat" below; the
reasoning above was the *starting* scope decision, not a claim the
combination was never tried at all. No alternative batch-correction
algorithm (RUV, limma's `removeBatchEffect`) was tried -- ComBat only, one
well-motivated method.

## A small, honest scope trim found during implementation

The pre-implementation edge-case list said the per-fold zero-within-batch-
variance cell count would be "recorded ... in the output CSV." It is not:
`mbhd.classifier`'s `fold_transform` hook signature is deliberately narrow
(`(x_train, y_train, batch_train, x_test) -> (x_train_corrected,
x_test_corrected)`) specifically so the held-out label leak above is
closed *through the API*, and threading an additional diagnostic value back
through it would have widened that same signature the whole design
exists to keep narrow. The substance of this finding is not lost --
the pre-implementation probe already gave the real, per-folder breakdown
(414 of 1,485 cells, 27.9%, every one of the 27 folders affected, worst
case `nash_chan_results` at 37/55 genera), which is
a more complete view (all 27 folders on the full feature space) than a
per-LOFO-fold CSV column would have given anyway (each LOFO fold only sees
26 of 27 folders' training data). Recorded here as a deliberate,
documented deviation from that pre-run wording, not a silent drop.

## Verification

`tests/test_batch.py` (20 tests): known-answer recovery (exact, without
empirical-Bayes shrinkage; directional, with it), the single-batch
identity case (mathematically degenerate for the general EB machinery,
handled explicitly), row-permutation and batch-relabelling invariance, the
real zero-within-batch-variance handling policy (confirmed non-crashing,
correctly pinned, correctly excluded from that batch's own prior fit), and
agreement with `pycombat` to ~1.4e-5 max absolute difference (mean ~3e-7)
with and without a covariate.

`tests/test_classifier_verification.py` adds three M5-specific tests: a
constant added to every held-out row's own features leaves that fold's AUC
exactly unchanged (a provable consequence of `StandardScaler` + a linear
classifier, not just a design intent -- confirmed, not assumed); the
`fold_transform` hook is called with exactly the training rows every fold;
and -- the test that actually closes the held-out label leak, not merely
asserts it by inspecting the signature -- flipping a held-out fold's own
labels (every other fold's own training labels held fixed) leaves that
fold's `mbhd.batch.combat_for_fold(..., use_covariate=True)` output
byte-identical.

`tests/test_no_reference_library_imports.py` extended: `mbhd.batch` never
imports `pycombat` at runtime, checked via subprocess the same way `mbhd`
never imports scipy/statsmodels.

**Regression:** `--features clr` without `--batch-correct` reproduces
`results/classifier/summary.json`'s pre-M5 blocks (`full`,
`shared_response_global_pool`, `shared_response`,
`disease_specific_global_pool`, `disease_specific`, `shared_response_clr`,
`within_study`) byte-for-byte -- diffed explicitly (`/tmp/m5_regression_
check`), not assumed from `fold_transform=None`'s default alone.

Full suite: 250 passed, `ruff check`/`format --check` clean (both before
the full run; later review changes are not reflected in this count).

## Appendix: tuned ComBat (tried, not adopted as the headline result)

A same-day follow-up asked the same question M4's own tuning appendix
asked, now of the adopted ComBat result: does `_tuned_pipeline`
(`class_weight="balanced"` + nested-CV-tuned `C`, `mbhd.classifier.
_tuned_pipeline`) improve on row 3 further? Wiring only — `mbhd.classifier
._run_arm`/`leave_one_group_out_auc_dynamic_features` already accepted
both `pipeline_fn` and `fold_transform` independently (M5's own original
design), so no new capability was needed in `mbhd.batch` or `mbhd.
classifier`; `scripts/classifier.py`'s prior `--batch-correct`+`--tune`
mutual-exclusion guard was removed and `_run_batch_correct_arms` gained
one optional `tune` keyword that adds a seventh row (row 3's own
`fold_transform`, tuned pipeline instead of plain).

**Generated by:** `uv run scripts/classifier.py --features clr
--batch-correct --tune`, run 2026-09-24. **pre-implementation timing probe** (3- and
10-repeat smoke runs, matching this project's established precedent for a
nested-CV-involving run): marginal cost ~37.4s/repeat, ~91s fixed
overhead, extrapolating to ~126 minutes for the full 200-repeat run. Real
run: **~1h56m** end-to-end — close to the estimate, and also the first
`--tune`-only computation since the `SAMPLE_TYPE_FILTER`/`CONDITION_FILTER`
fixes, refreshing M4's own previously-stale tuning appendix as a side
effect (`docs/reproduction-m4.md`).

| arm | mean AUC-ROC | mean AUC-PR | mean selected `C` | null mean / std | null std devs above |
| --- | --- | --- | --- | --- | --- |
| Row 3 (adopted headline: ComBat, plain) | 0.647 | 0.729 | — | 0.500 / 0.017 | ~8.5 |
| **Row 3 + tuned** | **0.659** | **0.732** | 0.000125 | 0.501 / 0.018 | **~9.0** |

**A real, checkable, additive finding:** ComBat correction alone
contributes +0.0125 AUC-ROC over the uncorrected CLR baseline (0.635 →
0.647); tuning alone (no correction) contributes +0.0112 (0.635 → 0.646);
applied together, the gain is +0.0239 (0.635 → 0.659) — the sum of the two
individual effects (+0.0237) to within 0.0002. The two levers appear to
be independent and additive on this data, not synergistic or
interfering — a real, quantified relationship, not asserted without the
arithmetic to back it. The selected `C` (0.000125) is smaller than the
already very small plain-CLR-tuned value (0.105, `docs/
reproduction-m4.md`'s refreshed appendix) — ComBat-corrected features are
more regularization-hungry still, consistent with the same collinearity
story already used to explain CLR's own regularization appetite.

**Not adopted, for the same reason M4's own tuning wasn't (Pablo,
2026-09-24, choosing explicitly between the two options rather than
defaulting to either):** a further gain of this size (+0.012 over the
already-adopted 0.647) is the same order of magnitude as M4's own
+0.011 gain, which was explicitly judged not to justify its added runtime
and complexity as the project's reported result. The same reasoning
applies again: 0.647 remains the clean, single-variable-at-a-time answer
to "does batch correction help" (one changed variable: the correction
method); stacking a second, independent lever (tuning) on top reintroduces
the same researcher-degrees-of-freedom concern M4's own appendix named.
**0.647 is what this project reports as its Part B answer** — 0.659 is
kept here, real and verified, as a further-gain finding, not the headline.

Per-fold numbers: `results/classifier/lofo_shared_response_clr_combat_
tuned.csv`, `permutation_null_clr_combat_tuned.csv`.

## Environment note: the dev-only ComBat oracle package

The original design named `inmoose` as the dev-only oracle. It failed to
install in this sandbox: no prebuilt wheel (sdist only), and its
`edgepy_cpp` Cython/C++ extension needs a compiler (`g++`) this
environment does not have and cannot install (no root, `sudo` requires a
password). Pablo chose `pycombat` (PyPI, BSD, pure Python, deps limited to
numpy + scikit-learn, both already installed) as the substitute after
being shown the tradeoff (lighter footprint but unmaintained since 2022,
vs. `inmoose`'s active maintenance but heavier dependency footprint, vs. no
oracle at all).
